# migrations/core — the central database's history

These are the migrations that built today's single database, moved here from
`migrations/` with `git mv` (db-per-company T5, model D-17). The only edit is
their relative import paths (`../src` → `../../src`), because each file now sits
one directory deeper.

- knex records a migration by basename in `knex_migrations.name`, so the move
  leaves every applied row valid: `npm run migrate:deploy` on an existing
  database reports "already up to date".
- Never edit, rename or delete an applied file. knex refuses to run ("migration
  directory is corrupt") when an applied name is missing, and production is
  roll-forward only (L-003): fix forward with a new file
  (`npm run migrate:create -- <name>`).
- A fresh core database replays all of this, including the business tables that
  tenants own. That is accepted; the alternative is rewriting applied history.
- Tenant databases never replay this set. They start from
  `migrations/tenant/00000000000000_baseline.ts`, generated by
  `src/scripts/generate-tenant-baseline.ts`. Replaying per tenant was rejected
  (D-17 option A) partly because `20251211000001_extend_warehouses_table.ts` and
  `20260120143704_add_company_id_to_master_tables.ts` cannot run without
  `companies`.
- `park_tenant_tables` and `drop_zz_old_tables` (C3/C4, applied in production
  2026-09-15) run wherever core is migrated. The park skips itself unless at
  least one company is registered and every live registration is a dedicated
  `tenant_*` database, so a fresh bootstrap or a local database still on the
  shared target keeps its business tables; the drop only removes `zz_old_*`
  tables and is a no-op where nothing was parked.
